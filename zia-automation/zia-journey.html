Twelve Stages to a Live CRM

The full route from an empty portal to a governed, reporting, self-reconciling CRM — in the order the dependencies actually force. Every stage lists the exact HubSpot path, the reason a specialist does it that way, what it produced in this portal, and what the free tier refuses to do.

Why the order matters

Most failed CRM builds are not failures of configuration, they are failures of sequence. Importing before the schema exists gives you free-text fields nobody can report on. Associating after the import means matching on a property that was never populated. Building dashboards before lifecycle stages are set gives you charts that count the wrong things confidently. The numbering below is a dependency chain, not a table of contents.

The business
Two-sided. Client organizations buy programmes; consultants deliver them. Both sides live in the same portal and must not be double-counted.
The constraint
Free tier. No workflows, no lists, no custom objects, one pipeline, no custom report builder.
The method
Probe, don't assume. Every tier limit here was discovered from an API response, and each one is named rather than hidden.

The route

01

Portal foundation and API access

Free tier

Settings → Account Defaults → currency, timezone, fiscal year
Settings → Integrations → Private Apps → Create private app → Scopes

Set account defaults before a single record exists. Currency and fiscal year retro-fit badly: deal amounts already stored are not re-denominated, and every date-grouped report silently re-buckets when the fiscal year moves.

Then create a private app rather than using a personal access key. A private app is scoped, revocable, and auditable — it belongs to the portal, not to a person who might leave. Grant only the scopes actually needed and add more when the API tells you to.

Say this Scope errors are the fastest way to learn HubSpot's product boundaries. Twice in this build a 403 named the exact granular scope missing — that is a configuration gap. A 403 on automation/v4 with the automation scope already granted is a different thing entirely: that is the tier, and no scope will fix it.
Gotcha. PowerShell 5.1 defaults to TLS 1.0 and every HubSpot call returns a bare 400 with no message. Set [Net.ServicePointManager]::SecurityProtocol=[Net.SecurityProtocolType]::Tls12 first.
02

Data model before data

Free tier

Settings → Properties → select object → Create property → choose group, field type, options

The single highest-leverage decision in any HubSpot build: every field a human will filter or group by must be an enumeration, not free text. A dropdown is a reportable axis. A text field is a landfill.

This portal carries 43 custom properties across four objects, and the seed data proved the point — 308 dirty zia_industry values arrived as ortho, Ortho, Orthodontics, three spellings of one sector. Normalised to canonical options, the field became groupable; as free text it would have produced a chart with three hundred bars.

The label / internal-name trap

HubSpot has a built-in Deal Type property. Our programme tier could not reuse that name, so the property is zia_deal_type with the label "Engagement Type". This matters more than it sounds:

  • The import UI matches CSV headers on the label — your CSV header must read Engagement Type.
  • The API matches on the internal name — your payload must read zia_deal_type.
  • Enumerations are written by internal value (core), displayed by label (Core). Send the label through the API and it fails silently or creates a junk option.

Prefixing every custom property zia_ makes "what did we add versus what shipped with HubSpot" a one-line filter forever.

03

Import, and the hygiene that has to happen first

Free tier

CRM → Contacts (or Companies / Deals) → Import → Start an import → File from computer → map columns → review errors

Import is where this build nearly went wrong, and the lesson is the most useful thing in the whole portal: validate the join key before you import, not after.

Say this A live search for a sample domain returned zero companies. Importing on schedule would have associated nothing and auto-created roughly 994 duplicate companies on top of the 20,551 already there. One search, run before the import, is what separated a ten-minute fix from a rebuild.
04

Associations — the part that makes it a CRM

Free tier

On any record → Associations panel → Add
API: POST /crm/v4/associations/{from}/{to}/batch/create

An unassociated record is a spreadsheet row. Associations are what let one question cross objects — "which client has the most at-risk engagements" touches company, deal, ticket and contact in a single hop.

Rather than trusting fuzzy matching, every deal was associated to its company by company id at create time. Result: 1,500 of 1,500 linked, zero orphans. Contacts carry a primary company association, which is the one HubSpot rolls up in reporting.

05

Lifecycle, pipelines and stages

One pipeline on free

Settings → Objects → Deals → Pipelines → edit stages
Settings → Objects → Contacts → Lifecycle stage

Lifecycle stage answers "how far through the relationship is this person", lead status answers "what is the next action". Teams routinely collapse the two and then cannot report on either. All 1,000 contacts carry both.

Here the tier bit hardest. A second deal pipeline returns 400 — free tier allows exactly one. So delivery engagements share the sales pipeline with new business, which is architecturally wrong and, left unmanaged, produces a fabricated 58.7% win rate. Handled honestly, acquisition win rate is 30.1%.

06

Commerce: products, line items, quotes

Free, with scopes

Commerce → Products → Create product
On a deal → Line items → Add → select from product library → Quotes → Create quote

A deal with an amount typed into it is a guess. A deal priced from line items is a quote you can defend, discount, and report on by product.

Seven products (three programme tiers, three consultant hour rates, one diagnostic), 1,500 line items across every deal, 578 discounted between 5–20%, and 531 quotes built from them. Discounting at the line level is what makes "are we buying business in the Summit tier" answerable.

Scope, not tier. Products first returned MISSING_SCOPES and it would have been easy to file that as a tier limit. It was not — enabling e-commerce and the product scopes unblocked it entirely. Quotes had the same story. Read the error body before you conclude anything.
07

Billing as an integration boundary

Commerce Hub required

Native: Commerce → Invoices / Payments — requires Commerce Hub and a connected payment processor

HubSpot Payments needs a US entity and a bank connection; Stripe needs a registered merchant account. Neither exists here — and a ledger does not belong in a CRM anyway. So billing is modelled at the boundary rather than faked.

Seven deal properties mirror invoice state back onto the deal — exactly the fields a QuickBooks or Xero integration writes. The CRM owns the relationship and contract value; accounting owns the ledger; RevOps reports on collections without leaving HubSpot.

09

Automation the tier will not give you

Workflows are Professional+

Native: Automation → Workflows — returns 403 on this tier
Here: node engine.js --dry-run → node engine.js

The automation scope is granted and gates nothing; workflows are a tier feature. So orchestration was externalised — seven rules running against the CRM API, with one design decision that matters more than all the others.

Every rule reconciles current state instead of reacting to an event. WF-03 does not ask "was a deal just won", it asks "which closed-won deals have no onboarding ticket". A missed run self-heals on the next pass, and re-running is safe by construction — the property a real workflow engine gives you for free, rebuilt deliberately.

Say this — the bug worth telling HubSpot returns association toObjectId as a number while object ids everywhere else are strings. Every dedupe Set.has(deal.id) silently missed. The dry run reported alreadyCovered: 500 and wouldWrite: 817 in the same breath — a contradiction that only existed on screen because the run was a dry run. Live, it would have created 817 duplicate tickets. Fixed once, centrally, so no rule can reintroduce it.

Proof it works: first live run wrote 317 onboarding, 115 compliance and 108 collections tickets. The immediate re-run wrote zero.

Documents on the record

Needs files scope

Settings → Integrations → Private Apps → Scopes → files (read + write), files.ui_hidden.read
On a record → Attachments → Add

A CRM with no documents on it is a CRM nobody actually works in. HubSpot models an attachment as a file plus a note carrying hs_attachment_ids, associated to the record — uploading a file alone puts it in the File Manager where nobody will find it.

Documents are generated as real PDFs from each record's own field values, so the SOW on a deal states that deal's contract value, seats and terms. 272 documents are live in the portal across 236 records.

Idempotency bug, found by re-running. The first version selected targets as "the first 50 records not yet covered", so every run walked further down the list — a second run added 125 more documents instead of zero. Selecting the target set first and subtracting what is already done makes it converge. Verified: the next run reported to attach: {}. Worth knowing that idempotency is a property of how you choose the work, not just how you dedupe it.
11

Reporting and dashboards

Custom builder is Professional+

Reporting → Dashboards → Create dashboard → Start from scratch
then Add report → Create custom report → Singular object

There is no public API to create a dashboard on any HubSpot tier — every version returns 404. Dashboards are a UI-only build, which makes the specification the deliverable. Eighteen reports across three dashboards, each named field verified to exist and be populated.

  1. Go to Reporting → Dashboards → Create dashboard.
  2. Choose Start from scratch — the templates assume a single-motion sales team and will not fit a two-sided delivery business.
  3. Name it, set visibility to Everyone, create.
  4. Add report → Create custom report → Singular object, then pick the object.
  5. Set the chart type, drag the field to the X axis, set the measure.
  6. Add the filters exactly as specified — this is where the win-rate error lives.
  7. Save, add to dashboard, then drag to size. Put the number leadership asks about top-left.
The one filter that carries the architecture On "new business won by month", filter Deal stage is Closed Won and Placement Status is unknown. Without that second clause you are adding delivery revenue to new sales, and every downstream number is wrong. It is one checkbox and it is the whole two-motion argument.

Full specifications for all eighteen reports — object, chart, axis, measure and filters — are in the companion Dashboard Build Guide.

Alongside the reports sit 9 saved segments, one per thing the engine acts on: consultants placeable now, consultants blocked by compliance, placements scoring below 60, invoices 90+ days overdue. A report tells you the shape of a problem; a segment gives someone the actual list to work through. The rule does the work, the segment is where a human looks.

Independent confirmation The segment Placements · scoring below 60 reports 144 — computed by HubSpot's own filter engine, with no involvement from our code. That is the headline finding reproduced by the platform itself, which is a far stronger thing to show than a number from a script.
If the custom builder is not offered, the account is on free. Build what you can from the standard report library and say plainly which reports need Professional. Naming the constraint is a stronger answer than pretending it is not there.
12

Governance, or it decays in a quarter

Data Quality Centre is Professional+

Settings → Properties → review unused
CRM → Contacts → Actions → Manage duplicates

Every CRM is clean on launch day. What keeps it clean is convention and a reconciliation job, not discipline.

  • Naming. Every custom field is zia_-prefixed and carries a description saying who writes it and when.
  • Enumerations over text, everywhere a human filters. This is governance, not preference.
  • Reconciling rules. The same engine that creates records also corrects drift, so state converges instead of decaying.
  • An audit trail. Every run appends to run-log.jsonl — what matched, what changed, what failed.
  • A validator. validate.js re-derives all 36 published claims from the live portal and fails loudly on drift.

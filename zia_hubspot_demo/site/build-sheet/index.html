Working document · build order for the trial portal

Lumen demo portal — build sheet

Everything to configure in a HubSpot trial so the system design in the walkthrough can be demonstrated live, in roughly a working day.

00

Before anything: what the trial can and can't do

read first

One capability gate shapes the entire build, so settle it before you configure a single property.

Custom objects require Enterprise. HubSpot gates Placement, Talent Profile and Cohort as custom objects behind an Enterprise subscription on at least one Hub, and that gating has not changed in 2026. A standard trial is Professional. So build the trial portal with standard objects, and present the custom-object model as the target architecture.

This is not a weakness in the demo. Showing a working Professional-tier build and naming the Enterprise target is exactly what a senior architect does — it proves you cost the design before you propose it. Say it in one line during §03 and move on.

Target architecture → trial substitute
Target (Enterprise)Build in the trial asWhat survives the swap
Placement A second Deal pipeline named "Placements — Delivery". One deal record = one embedded person. Everything: stages, properties, automation, recurring-revenue reporting, health score. This is the strongest substitute.
Talent Profile Contacts where contact_type = Talent, plus a talent property group. Matching, bench reporting, availability. Loses the clean 1:1 separation, which is the honest trade to name.
Cohort A static list per cohort plus cohort_name / cohort_status contact properties. Fill and completion reporting. Loses many-to-many across multiple cohorts per person.
Also verify in your own portal rather than trusting a guide: whether the workflow webhook action and custom coded action are enabled — both are Operations Hub features and their availability differs by trial. If webhooks aren't there, demo the ClickUp step as a task-creation action and say what it would be in production. Never demo a step you had to fake.

03

Seed data

~45 min

A demo dies on empty dashboards. Load enough realistic data that every report has shape — but use clearly fictional practice names, never real clinics.

Volume that reads as real: 10 companies, 20 client contacts, 15 talent contacts, 12 acquisition deals across all stages, 9 placement records (6 active, 1 at risk, 1 ended, 1 awaiting match), 2 cohort lists. Spread createdate and close dates across the last six months so trend charts have a line to draw.

04

Workflows

~2 hrs
Automation → Workflows

Six workflows. Build them in this order — each depends on the one before. Name them with a team prefix so the list reads as an architecture rather than an accumulation.

WF-01 · Sales

Match & Embed — the one you demo live

Trigger
Deal stage = Closed Won in the Client Acquisition pipeline
Actions
  1. Create a Deal in the Placements pipeline at Awaiting Match, copying tier, hourly rate, hours per week, and associating the same company
  2. Set hourly_rate by tier: 12 / 16 / 22
  3. Create tasks for the onboarding set — systems access, comms channels, payroll setup — each assigned and dated relative to enrollment
  4. Enrol client contacts in the welcome sequence, filtered to contact_type = Client Contact
  5. Send internal notification to talent ops with the tier and hours required
  6. Webhook to ClickUp if available — otherwise a task, and say so in the demo
Watch for
Set re-enrollment off. Without it, editing a won deal spawns duplicate placements — a mistake worth mentioning aloud, because catching it is the architect's instinct.

WF-02 · Data quality

Contact type enforcement

Trigger
Contact created
Actions
Branch on form source and source_line to set contact_type. Anything unresolved is set to Unclassified and raises a task, so the gap is visible instead of silently defaulting to Client Contact.
Why it's first
Every downstream list and sequence filters on this property. If it's wrong, Break 01 from the walkthrough happens in your own demo portal.

WF-03 · Sales

Fit score routing

Trigger
fit_score is known and deal stage = Role Defined
Actions
Score ≥ 10 → move to Showcase Scheduled, notify the owner, book the showcase. Score 4–9 → enrol in the nurture built around their two weakest criteria. Score < 4 → task to disqualify with disqualifier_reason required.

WF-04 · Customer success

Check-in cadence

Trigger
Placement deal reaches Kickoff Scheduled
Actions
Dated tasks at day 7, 30 and 90, then quarterly. CSAT survey at day 30 and 180. Each completion stamps last_checkin_date. An overdue check-in past 14 days notifies the CSM's manager.
Demonstrates
Lumen’s published "ongoing check-ins" promise, running as a system behavior rather than a good intention.

WF-05 · Customer success

Placement health scoring

Trigger
Daily schedule across all Active placements
Actions
Score from check-in recency, CSAT trend, open escalation count, and hours-logged versus contracted. Below floor → set status At Risk, alert the CSM, create a dated task. Above ceiling with positive scope drift → create a tier-upgrade task for sales.

WF-06 · Education

LumenU enrollment on Steady State

Trigger
Placement reaches Steady State
Actions
Add the placed talent contact to the current cohort list, set cohort_status = Enrolled, send the access email.
Why include it
It's the only workflow that touches the Education department the JD names, and it closes the loop on the support model's second promise. Small, but it shows you read all five departments.
05

Forms, meetings and the front door

~40 min

Lumen already runs two conversion actions on their site — "Book a 15-Min Alignment Call" and "Schedule a Talent Showcase." Build both, because it shows the design starts where their traffic actually lands.

  • Alignment Call meeting link with the qualification questions embedded as booking fields — practice type, team size, what role is falling through the cracks. The rep arrives at the call with the scorecard half filled.
  • Talent Showcase form, gated slightly harder: tier interest and hours per week required, because a showcase request is a genuine buying signal and deserves faster routing.
  • Talent application form writing contact_type = Talent directly, so the two audiences separate at the point of entry rather than by cleanup later.
  • Hidden UTM fields on all three, mapped to source_line, so attribution works from day one instead of being retrofitted.
One flourish worth the ten minutes: set the alignment-call booking confirmation to send a short "how to prepare" email listing the six fit criteria. It qualifies the prospect before the call, it uses Lumen’s own words, and in the demo it lets you say the system starts doing the qualification work before anyone picks up the phone.

07

The live demo run

6 min of the call

Rehearse this until it runs without hesitation. Have the deal pre-staged at Agreement Sent, both browser tabs open, notifications enabled. If a step fails live, narrate what it does and move on — recovering calmly reads better than a flawless run.

  1. Open on the executive dashboard.Note the current recurring revenue figure aloud. You're establishing a before state that will visibly change.
  2. Open the Meridian Ortho Group deal at Agreement Sent.Point at the fit scorecard in the sidebar — twelve fields, Lumen’s own criteria, a score of 14. Thirty seconds, no more.
  3. Drag it to Closed Won.Say nothing for a beat. Let the workflow run.
  4. Show the placement record that appeared.Tier, rate, hours, monthly value already calculated. This is the Deal-versus-Placement distinction, made concrete.
  5. Open the talent ops notification.Three bench-ready Momentum profiles in the right timezone, ready for a Talent Showcase. Their process step three, automated.
  6. Show the onboarding tasks and the check-in cadence already scheduled.Day 7, 30, 90. Their published support promise, now a system behavior.
  7. Return to the executive dashboard and refresh.Recurring revenue up, one more active placement, time-to-placement clock started. Close on this — the whole argument is that leadership sees it without asking anyone.
Do not demo: anything you built at 2am and haven't run twice. A four-step demo that works beats a seven-step demo that stalls. Cut steps 5 and 6 before you cut steps 3 and 7.

Build order matters more than build completeness. Properties, then pipelines, then seed data, then workflows — anything built out of that order gets rebuilt. If time runs short, ship WF-01 and the executive dashboard, and present the rest as design.

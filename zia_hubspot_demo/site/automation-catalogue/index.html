01

Workflow enrollment

What starts an automation

Enrollment is where most workflows go wrong. A trigger that's too broad re-enrolls records and duplicates work; one that's too narrow silently misses cases. Both failures are invisible until someone notices the data is wrong.

Enrollment triggers
Trigger typeUsed here forStatusNote
Property-basedDeal stage becomes Closed Won → Match & Embed firesBUILTThe primary trigger in the build
Object createdContact created → contact type enforcementBUILTRuns before anything else can act on the record
Form submissionShowcase request → fast-track routingBUILTDistinct forms carry distinct intent
List membershipEntering an at-risk placement list → CSM alertDESIGNEDUseful when the criteria are complex enough to be worth naming once
Activity-basedEmail opened / page viewed / call logged → engagement scoringDESIGNEDBehavioral half of the fit score
Scheduled / recurringNightly placement health recalculationBUILTBatch work belongs on a schedule, not on a record trigger
Date-basedEmbed start date + 7 / 30 / 90 → check-in cadenceBUILTAnchored to a property date, not to enrollment time
Meeting booked / outcomeAlignment call booked → SQL, prep task, fit scorecard surfacedBUILTTheir front door is a meeting link, so this matters
Webhook / API enrollmentExternal system pushes a record into a workflowTIERThe integration path when a partner system owns the event
Manual enrollmentCSM triggers a continuity handover packDESIGNEDDeliberately human — not everything should fire itself
Re-enrollment is the trap. On Match & Embed it is switched off: without that, editing a won deal spawns a second placement record and the recurring-revenue number silently doubles. On the check-in cadence it is switched on, because a placement genuinely should re-enter the cycle. Knowing which is which per workflow is most of the craft.

Programmable automation

Where the UI runs out

The line worth being able to draw in an interview: use the UI until the logic can't be expressed there, then write code — and be able to say precisely where that line falls and why.

Code-level automation
CapabilityUsed here forStatusNote

Custom coded actionComposite health score from four weighted signalsTIERWeights live in one function, not scattered across branches

The judgment, stated: code is used in exactly three places — ranking, composite scoring, and provisioning. Everywhere else the UI is better, because a workflow a HubSpot admin can read and change beats a function only its author understands. Choosing not to write code is an architectural decision too.

The principle, in one line: AI proposes, a human commits, the CRM records who committed it. The three declines above are worth stating out loud in the interview — knowing where not to automate reads as more senior than automating everything.

Scope delivered

What this engagement produced, and where its limits are

A summary of the work, the artifacts it produced, and the assumptions that would need validating against a live portal before any of it is committed to a delivery plan.

Coverage by Hub

Functional coverage
HubWhat the design coversDepends on

Artifacts produced

  • Object model and entity-relationship design — three custom objects, the contact-type discriminator that separates the two audiences, and the Deal-to-Placement separation that makes recurring revenue reportable.
  • Nine workflows, specified end to end with triggers, actions, branch logic, re-enrollment settings and suppression rules.
  • Portal provisioner — a declarative JSON schema and an idempotent script that creates every property group, property and pipeline through the CRM API, making the whole structure version-controlled and reproducible.
  • Portal auditor — a read-only diagnostic that reports property fill rates, free-text fields that should be constrained, unowned records, stalled deals and single-pipeline anti-patterns, and writes a findings report.
  • Shortlist ranking action — deterministic candidate scoring on tier, capacity, timezone overlap and functional match, with server-side filtering to stay inside execution limits.
  • Reporting specification — eight executive metrics with stated formulas, four department dashboards, and a CRM health monitor sharing definitions with the auditor.
  • Economic model — an interactive tool quantifying recurring revenue visibility, churn exposure and automation return, with its own assumptions documented.

The process problem this addresses

The situation. A services business whose revenue comes almost entirely from recurring delivery was forecasting on deal amount — the one component of the transaction that occurs once. Current recurring revenue, gross margin per engagement, and which engagements were degrading were all unanswerable without manual reconstruction.

The intervention. Separate the sale from the delivery by introducing a Placement record with its own lifespan, rate, hours and health score. Automate the handoff at Closed Won so the record is created with the data already on it. Add nightly health scoring so degradation surfaces before it becomes churn.

The result. Recurring revenue and margin become reportable properties rather than spreadsheet exercises. At-risk engagements appear on a worklist weeks before they end. Coordination work at each new placement drops from a manual chain to a single trigger. The economic model quantifies each of these against the client's own figures.

Known limits

  • Subscription tier is unconfirmed. The custom-object model requires Enterprise. A Professional fallback using a second deal pipeline is specified and retains most of the design, but which path applies cannot be settled without portal access.
  • Existing data quality is unknown. Migration scope, duplicate volume and back-fill effort all depend on audit findings that require a token to produce.
  • Attribution can only begin where UTM capture exists. If forms do not currently carry hidden UTM fields, historical attribution is unrecoverable and the model starts from implementation date.
  • Health-score intervention rates are hypothetical. Scoring surfaces at-risk placements; whether intervention succeeds depends on people, not the CRM. The figure should be measured over two quarters rather than assumed.
  • Integration behavior is specified but untested against the actual project tool in use, and webhook availability varies by subscription.

This catalogue is not an argument that everything should be automated. It exists so that every capability HubSpot offers has been considered against a specific job in this system — including the several where the correct decision was to leave the work with a person.
